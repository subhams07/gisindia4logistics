# N2 Linux addendum — containment, parent death, termination and telemetry

Addendum to [the N2 resource specification](stage4_n2_resource_spec.md) (sections F, G, H) for the Linux cloud host recorded in [the handoff](claude_remote_handoff.md) section 0. **Design only: not reviewed, not approved, not execution authority.** No harness exists. Sections A–E and I–J of the base spec apply unchanged except where a row below says otherwise. Every "smoke-verify" item is unproven on this host and must be proven by the synthetic native smoke before a real run is considered.

Terminology: *attempt cgroups* = the per-attempt cgroup set owned by the controller; *controller* = the coordinator-owned dispatch process; *direct child* = the process the controller forks; *producer* = the Python process that runs the slot (PID 1 of a new PID namespace, see L-4).

## 0. Host facts the design depends on

Survey and probes, 2026-10-17 (exact probe commands in section 9):

- Kernel 6.18, cgroup **v1** controllers mounted separately: `memory`, `pids`, `freezer`, `cpu`, `cpuacct`, `cpuset`, `blkio`, `devices`; plus a cgroup2 mount at `/sys/fs/cgroup/unified` whose only controller is `hugetlb`.
- The Bash tool's processes live in memory cgroup `/process_api/<id>/claude-code-bash`, which has a **13,358.4 MiB (`14343688192` bytes) platform limit**, `use_hierarchy=1`. Its parent (`/process_api/<id>`, holding the Claude Code process) and the root have no limit. PID 1 is the platform's `process_api`, not systemd. pids/freezer membership of the Bash tool is the root `/`.
- Host: 15.7 GiB `MemTotal`, no swap, `overcommit_memory=0`, `pid_max=32768` (PID reuse is realistic), THP `madvise`, `panic_on_oom=0`. Seccomp off, full capability set, util-linux 2.39.3 (`unshare --pid --fork --kill-child` available). `/` shows 29 GiB available.
- Python 3.11.17 has `os.pidfd_open`, `os.waitid`, `os.P_PIDFD`. It has no `os.unshare` (that arrived in 3.12).
- An empty child cgroup can be created under the Bash tool's memory cgroup and under the pids root. A process written to `cgroup.procs` shows the new paths in `/proc/<pid>/cgroup`. Counters start at zero. `memory.max_usage_in_bytes` and `pids.peak` record a peak the kernel maintains itself. Allocations made **before** joining stay charged to the old cgroup (`move_charge_at_immigrate=0`). After the process exits, some page cache stays charged (753,664 B), and `rmdir` still works.

Consequence: the limit that actually binds is the platform's 13.36 GiB cgroup, not host RAM, and an OOM there could kill the controller, the shell or other session processes. The design therefore puts a hard limit on each attempt's own cgroup below that ancestor.

## 2. Resolving the section F cleanup ambiguity (Linux)

The Windows overlap was an attempt that has been assigned but not yet resumed. On Linux the states are separate and named:

| State | Entered when | Only permitted termination |
|---|---|---|
| S0 forked-gated | `fork` returned | pidfd SIGKILL + `waitid` (exact-handle exception) |
| S1 assigned | freezer membership **verified** (the first controller joined is the one that can kill) | cgroup termination (section 3); the pidfd is used only to wait and reap |
| S2 released | gate byte written | cgroup termination (section 3) |

Proposed ruling **R-1**: kill authority moves to the cgroup exactly at S1, and the exception for exact-handle cleanup covers **S0 only**. If writing the launch record or starting telemetry fails at S1, cleanup goes through the cgroup, which in that state contains only the gated child. That satisfies both constraints at once without widening the exemption. If joining memory or pids fails, the attempt is still in S1 and is cleaned up through the cgroup. Closing the gate (EOF → `_exit`) may come first as a non-signal step, but it does not replace the cgroup kill and the empty-cgroup check. **Reviewer and operator must confirm R-1**; it is a proposal, not a ruling that has been made.

## 3. Termination procedure (S1/S2)

1. Graceful: write `FROZEN` to `freezer.state`, wait (≤ `freeze_wait_s`) until it reads back `FROZEN`, then read `cgroup.procs`. Send SIGTERM to the member whose `/proc/<pid>/status` `NSpid` ends in `1` (the namespace's PID 1 ignores signals it has no handler for, so the stub installs a SIGTERM handler). Thaw, then wait up to `graceful_wait_s` for the cgroup to empty.
2. Hard: freeze, read the listing, send SIGKILL to **every** member, thaw (v1 freezer delivers the kill on thaw), and wait up to `cgroup_kill_wait_s` for `cgroup.procs` to be empty and the direct child to be reaped.
3. If the freeze does not reach `FROZEN` within `freeze_wait_s` (for example a task stuck in D-state): proposed **R-2** escalation is pidfd SIGKILL to the direct child (`unshare`). The kernel then sends PDEATHSIG to the namespace's PID 1, and its death tears down the namespace. This is a new exact-handle use after S1, so it **needs an explicit ruling**. Without R-2, the default is STOP and report survivors, with no further action.
4. Survivors after step 2/3 → STOP with the cgroups preserved. No rmdir, no unrelated kills.

## 4. Section G mapping — telemetry and the "private commit" analogue

**Why there is no Windows private-commit equivalent.** `PagefileUsage` is private virtual memory charged against a commit limit that the system enforces whether or not the pages are touched. On this host, with heuristic overcommit and no swap, commit is neither charged nor enforced: untouched reservations cost nothing, and the binding resource is pages actually charged to a memory cgroup (anonymous + page cache + kernel). Exhaustion shows up as an **OOM kill (SIGKILL)** in the attempt cgroup or an ancestor, rarely as `MemoryError` (which needs an mmap refused by the heuristic or by `RLIMIT_AS`). RSS is not private commit either: it includes shared file-backed pages (libraries, mmapped files) and excludes page cache charged to the cgroup. No Linux field may be called "private commit".

**Chosen analogue — "charged memory", in three fields, none renamed from Windows:**

| Field | Source | Role |
|---|---|---|
| `cg_charged_peak_bytes` | attempt `memory.max_usage_in_bytes` (cross-check that `memory.memsw.max_usage_in_bytes` is equal; a mismatch is an anomaly STOP) | **Primary peak gate metric**: the kernel maintains it, polling cannot miss a spike, and it is conservative because it includes page cache and kernel memory. Replaces `PeakPagefileUsage` in its *role*, not its meaning |
| `cg_anon_bytes` (current, sampled peak) | `memory.stat` `total_rss + total_shmem` | Closest to "private" on a host without swap (anonymous memory that cannot be reclaimed). Its peak is sampled, so it can miss spikes (disclosed) |
| `proc_*` per member | `/proc/<pid>/status` `VmRSS`, `VmHWM` (kernel peak), `RssAnon`, `RssFile`, `RssShmem`, `VmData`, `VmPeak`, `Threads` | Working-set analogue (`VmRSS`/`VmHWM`) kept separate. `VmData`/`VmPeak` are reported as *virtual reservation*, are not enforced and do not gate. `ru_maxrss` from `wait4` is recorded at reap |

Also recorded: `memory.usage_in_bytes`, `memory.stat` `total_cache`/`total_mapped_file`/`total_dirty`/`total_writeback`, `memory.kmem.usage_in_bytes`/`max_usage_in_bytes` (assumed included in usage; smoke-verify M14), `memory.failcnt`, `memory.oom_control` (`under_oom`, `oom_kill`), `pids.current`/`pids.peak`/`pids.events`, `freezer.state`, the `cgroup.procs` set with starttimes, and the direct child's state via pidfd poll.

**System-commit-available analogue:** `effective_available_bytes = min(host MemAvailable, min over every ancestor memory cgroup of the attempt with a finite limit of (limit − usage_in_bytes))`. Record each term separately. Ancestor usage includes reclaimable cache, so this is conservative; `MemAvailable` is a kernel estimate. `CommitLimit`/`Committed_AS` are recorded for information and labelled *not enforced*. Separately: `attempt_headroom_bytes = attempt limit − attempt usage_in_bytes`, and scratch filesystem `statvfs` `f_bavail*f_frsize`.

**Page-cache pitfalls (disclose; tested in M14):** (a) a page is charged to the cgroup that first touches it. Inputs the parent hashed before dispatch are already cached and charged to the *controller's* cgroup, so the child's charge **underestimates** a cold read, while a cold host overestimates relative to a warm one. (b) Writes are charged as dirty cache until writeback completes. (c) `failcnt` counts every time the limit is hit, **including hits fully absorbed by reclaiming cache**, so it is not an OOM signal (`oom_kill`/`under_oom`/SIGKILL are). (d) Cache from earlier attempts stays charged after exit (probe: 753,664 B); every attempt therefore gets a fresh cgroup, never reused. No `drop_caches` or `force_empty` (they change the host or are destructive).

**Sampling and failure semantics:** one sample = the set above plus a monotonic ns and realtime timestamp, a sequence number and the member PIDs. If any read fails while the pidfd shows the child still alive → telemetry loss STOP (never zero, never omitted). A `/proc/<pid>` ENOENT for a member that has exited (according to the pidfd, or because it is absent from `cgroup.procs`) is recorded as an exit, not as loss. Gaps over `max_sample_gap_ms`, or a sequence/clock that goes backwards → STOP. Phase boundaries come from the stub's stderr markers, which carry the same monotonic clock, plus a boundary sample triggered by the controller. An optional `cgroup.event_control` eventfd on `memory.oom_control` gives OOM notice without waiting for a sample (smoke-verify). Attribution rules from section G are unchanged.

**STOP mapping (Linux):** real `MemoryError`; `ENOSPC`/`EDQUOT`; `oom_kill` delta > 0, `under_oom=1`, or member death by SIGKILL not sent by the controller; `EAGAIN` on fork/thread creation or `pids.events max` delta > 0; `ImportError`/`OSError` loading shared libraries; more than the expected processes in `cgroup.procs` (producers spawn no subprocesses, as checked by grep); telemetry loss or gap; floor or time breach; unexpected exit; missing receipt; the section D cache latches; unsafe roots; hash or identity drift; concurrency (another `n2-*` cgroup exists, or another writer).

## 6. Synthetic controls

M01, M02, M05, M06, M07, M10 and M11 are unchanged in intent, with these Linux wording changes: M02's records gain the Linux bindings from section 1. M04 "reparse rejection" becomes rejection of symlinks and mountpoints (`lstat`, `O_NOFOLLOW`, `st_dev` change of an ancestor), plus refusal of any root under `/sys`, `/proc` or `/dev`. M11 adds: the repository tree contains no `n2-*` cgroup state.

**M03-L (replaces M03).** L1 attempt record before `mkdir`; `mkdir` EEXIST → STOP. L2 limits read back exactly; injected limit-write failure consumes and removes only empty cgroups this attempt owns. L3 fork refused when the controller has more than one thread. L4 the gated child has not exec'd (`/proc/<pid>/exe` is still the controller interpreter and the cmdline is the controller's); injected gate EOF → `E_GATE` with no exec. L5 join order freezer → memory → pids, verified two ways; injected join failure at each controller follows R-1 (S0 pidfd versus S1 cgroup). L6 launch record and `k` valid samples before release; injected telemetry failure at S1 → cgroup cleanup, no release. L7 stub refusals: wrong cgroup, not PID 1, missing PDEATHSIG, `PYTHONPATH` set, each → its fixed code before `site.main()`. L8 fd audit: only fd 0–2 open in the stub (`/proc/self/fd`). L9 graceful, hard and R-2 paths (R-2 only if ruled); empty cgroup and reaped child at the end. L10 `-S` plus `site.main()` gives the same `sys.path` as a normal venv start. L11 an unrelated stdlib sleeper started by the test, outside the cgroup, with a PID adjacent to the child's, survives every kill path. No `kill` from a PID that did not come from a frozen listing or the pidfd (static check).

**M08-L (replaces M08).** Unit conversion (`/proc` kB → bytes ×1024; cgroup files are already bytes; the `max` token in pids). The fields `cg_charged_peak_bytes`, `cg_anon_bytes`, `VmRSS`/`VmHWM` and `VmData` are distinct and none is labelled commit. Injected unreadable file / parse error / child alive → STOP. ENOENT for a member that has exited → recorded as an exit. Missed, duplicated and out-of-order sequence numbers and a monotonic clock going backwards are detected. `effective_available_bytes` follows the min-of-ancestors formula, with a fake ancestor tree in a mock sysfs root.

**M09-L (replaces M09).** Injected test-policy crossings, strict and inclusive, for each section 5 floor. Gap and elapsed expiry. Detection of OOM, `pids.events max`, `EAGAIN`, `ENOSPC` and library-load signatures from **injected neutral labels on mock counters**. The section D cache latch. Exit without a receipt. `failcnt>0` without `oom_kill` is handled according to `failcnt_action`, not as OOM.

**New controls:**
- **M12 cgroup lifecycle.** An existing `n2-*` cgroup (populated or empty) at controller start → STOP with a report and no cleanup. A unique name per attempt; no reuse. A failed `rmdir` → STOP. A controller cgroup path that is not under the paths recorded at prepare → STOP.
- **M13 parent death.** Real stdlib child: SIGKILL the **controller** (in a test that is itself run under a test parent) at S0, at S1 and after release. Expected: S0/S1 → the child never execs (gate EOF/PDEATHSIG); after release → the namespace is gone and the cgroup is empty within a measured time; the next start sees the leftover cgroup and STOPs (M12). Includes a grandchild spawned inside the namespace by the synthetic child, to prove the namespace teardown kills it.
- **M14 accounting semantics.** Real stdlib child: allocations before joining are not charged (matches the probe). Allocate N MiB after joining → `cg_charged_peak_bytes ≥ N` and `cg_anon_bytes` reflects N. Reading and writing a few MiB scratch file raises `total_cache`, not `total_rss`. kmem is included in usage. Residual cache after exit is reported.
- **M15 confined OOM (needs explicit approval, Q-O4).** A stdlib child in an attempt cgroup limited to a few tens of MiB allocates past the limit: the in-cgroup OOM kill is detected through `oom_kill`, SIGKILL and an optional eventfd, and the controller, the shell and the unrelated sleeper survive. This is a real but tiny and confined OOM, not host exhaustion.

Allowed native smoke, Linux: stdlib-only children that allocate a few MiB and sleep, exercising the real cgroups, gate, PID namespace, telemetry and termination paths. No repository producer imports, national reads or models.

## 7. Open questions

Operator:
- **Q-O1 Ledger durability.** The container is ephemeral; losing it erases the consumption records. Should attempt/launch/terminal records be copied off-host (private) before each release? Is losing a ledger acceptable as "consumption unknown → no dispatch without a new ruling"?
- **Q-O2 Controller lifetime.** The Bash tool kills foreground commands at ≤600 s and background ones at ≤7,200 s. Its death is the parent-death path, so every slot ends. Is `per_slot_elapsed_cap_s` bounded by that, or may the controller be detached (`setsid`)? `systemd-run` is unlikely to work because PID 1 is not systemd. Detaching weakens "parent death ends the attempt" and needs review.
- **Q-O3** Is the "charged memory" analogue (section 4) accepted as the gating basis in place of private commit? Insisting on commit-enforced semantics is not achievable on this host → NO-GO here.
- **Q-O4** Approve M15's confined OOM smoke?
- **Q-O5** The reserve for the Claude Code process and session processes inside the platform cgroup, and whether the platform (`process_api`, `sbx-telemetry`) may itself intervene in or limit processes. That behaviour is unknown and undocumented here.
- **Q-O6** Approval for the Python 3.11 venv install (needed only for the later real profiles; the synthetic smoke is stdlib-only).

Reviewer:
- **Q-R1** Confirm R-1 (S0-only exact-handle exception) and rule on R-2 (pidfd escalation when the freeze fails).
- **Q-R2** Is pre-exec controller code in the forked child acceptable as the analogue of "suspended"? Is `-S` + deferred `site.main()` the right reading of "first statements stdlib-only"?
- **Q-R3** Should `cg_charged_peak_bytes` (which includes cache) or `cg_anon_bytes` (sampled) gate the running floors? How should the parent's pre-dispatch hashing, which leaves inputs cached and charged to the controller, be treated?
- **Q-R4** If CLONE_NEWPID is unavailable: accept PDEATHSIG + the one-process invariant + M12 as a fallback with a disclosed residual risk (an orphaned grandchild after controller death), or NO-GO?
- **Q-R5** Is the cgroup v2 `cgroup.kill` in the `unified` mount worth adding as the primary hard kill, if smoke proves the process can be a member of it?
- **Q-R6** Confirm that `oom_score_adj=1000` on the child is not a forbidden "host setting" (it is a property of the process only).

## 8. NO-GO conditions

NO-GO for any real profile if any of the following holds: a freezer child cgroup cannot be created, frozen and thawed; an attempt memory limit cannot be set and read back, or cannot sit below the binding ancestor with the agreed reserve; membership cannot be verified before release; CLONE_NEWPID is unavailable and Q-R4 is not ruled; Q-O1 or Q-O2 is unresolved; any M03-L, M08-L, M09-L or M12–M14 control fails (M15 too, if approved); telemetry cannot be read completely at the measured interval; the operator requires Windows commit semantics; or platform intervention (Q-O5) is observed during smoke. A NO-GO is a valid outcome; the alternative is a host that can meet the base spec.

## 9. Probe record (designer session, 2026-10-17)

Read-only: `uname -r`; `cat /proc/self/cgroup /proc/cgroups`; `mount | grep cgroup`; `ls /sys/fs/cgroup/{,memory,freezer,pids,unified}`; `grep MemTotal|MemAvailable|SwapTotal|Commit /proc/meminfo`; `/proc/sys/vm/overcommit_{memory,ratio}`, `vm/panic_on_oom`, `kernel/pid_max`; `nproc`; per-level reads of `memory.{limit_in_bytes,memsw.limit_in_bytes,usage_in_bytes,max_usage_in_bytes,use_hierarchy,oom_control,swappiness,move_charge_at_immigrate}` for root, `process_api`, `process_api/<id>` and `…/claude-code-bash`; `memory.stat` of `claude-code-bash`; `unified/cgroup.controllers`; `df -h`; `unshare --version/--help`; `prlimit --version`; `grep Cap|Seccomp|NoNewPrivs /proc/self/status`; `ps -e`; the cgroup of the parent process; THP mode; Python 3.11 `os` capability check (`python3.11 -I -c …`); and a grep confirming the producers use no `subprocess`/`multiprocessing`/thread pools. Results are in section 0.

Mutating (permitted scope only): created `…/claude-code-bash/n2-design-probe-f5af6aea` (memory) and `/sys/fs/cgroup/pids/n2-design-probe-f5af6aea`, and read their files (all limits unlimited/`max`, counters 0, `oom_control` shows `oom_kill 0`, `pids.peak` present).
